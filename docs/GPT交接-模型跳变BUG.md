# 模型跳变 BUG — GPT 交接文档

> 生成时间：2026-09-29 深夜（含当天实测数据）
> 项目：openpilot（0.11.x）移植到 Mac，端到端驱动网页游戏 slowroads.io
> 目的：模型覆盖层会周期性"跳"到一个**固定幻觉状态**（4 条车道线全亮 + 一辆不存在的车），本机已做两轮修复仍未根除，需要外部协助定位。

---

## 1. 症状（用户视角）

- op 的覆盖层偶尔"跳"到固定状态：**4 条车道线全部亮起 + 约 69 米处出现一辆假车（黄色三角前车标记）**，诱发莫名的刹车和方向修正（slowroads 里没有其他车，任何检出的车都是幻觉）。
- 表现两种形态：**闪动**（快速进出，几帧）和**长时间显示**（锁定几十秒不动）。
- 用户报告：与"卡顿"相关；但**窗口焦点在游戏上时也会发生**（排除 App Nap 单一因素）。

**固定状态的精确数值（关键指纹）：**
```
laneProbs = [0.85, 0.96, 0.90, 0.22]   （4 条车道线概率）
leadProb  = 0.54,  leadX = 69.31 m     （幻影前车）
```
跨小时、跨多次独立漂移事件**逐字节一致** —— 这是循环网络的一个**固定点（吸引子）**，不是随机噪声。

---

## 2. 系统架构（数据流）

```
slowroads.io (网页游戏)
  └─ GameWindow.app (自研 WKWebView 壳)
       ├─ 20fps 定时 takeSnapshot 画布 → JPEG → 原子替换写 live_frame.jpg
       └─ 每 5 帧一次 Vision OCR（从 HUD 读车速）→ game_speed.json
  └─ openpilot webcam camerad（把 live_frame.jpg 当"摄像头"）
       └─ 解码 → 1928×1208 NV12 → visionipc 窄路流
            └─ modeld（driving_supercombo，已转 CoreML/ANE fp16）
                 └─ modelV2 输出 → op UI 覆盖层 + 控制
  └─ 假车桥 fake_car_bridge.py（OCR 车速等 → carState/传感器 → op 以为在开车）
  └─ op 通过页面内伪装的 Gamepad API 真正控制游戏（不碰鼠标）
```

**模型的关键属性：**
- **循环网络**：每次推理输出内部状态，回灌下一次推理（CoreML 路径在 `coreml_runner.py` 里显式 `assign` 回灌）。
- **输入不含任何时间戳/帧间隔信息**：模型不知道帧间隔是多少，按 **20Hz** 训练（帧间约 0.4–0.8m 运动，真实道路图像）。
- 状态形状：`state_img_q (2,5,6,128,256)`、`state_feat_q (96,1,512)`、`state_desire_q (100,1,8)`。
- warp（透视变换）走 tinygrad；推理走 ANE（4.36ms/帧）。

## 3. 已确认的实测事实

### 3.1 吸引子的存在（注入实验，2026-09-29 21:55）
往 `live_frame.jpg` 写受控序列，用记录器抓模型实际收到的帧 + 每帧输出：

| 注入序列 | 结果 |
|---|---|
| 两张差异大的图快速交替（F/A @20fps，15s） | **不漂**，模型在两三个状态间来回响应 |
| 同一张图重复（@20fps） | 相机去重全拦，模型根本看不到 |
| **稀疏跳帧**（每 1.2s 一张，大变化） | **漂移**，回到固定状态 |
| 慢爬（F 与微改版 F2 交替，单帧差异 ~1.5%） | 前期漏入的部分帧把模型带进了固定状态 |

### 3.2 修复后的真实行驶数据（2026-09-29 22:18–22:32，60km/h，仍在漂）
- 13 段漂移事件，**最长 66 秒**（22:29:32–22:30:38，115 次漂移签名帧）。
- **漂移是"进出交替"的**：记录显示模型在固定状态和正常状态之间来回翻转（这正是"闪动"），所以"输出连续一字不差"的检测抓不到它。

### 3.3 输入帧率的真相（帧分析，漂移窗口 22:32:24–29）
- **游戏窗口实际只渲染 ~7–11 fps**（帧间隔 86–253ms）；快照定时器 20fps 在重复捕捉同一帧，日志里出现「跳过 132 帧重复帧」。
- 帧间变化：高速段 **20–30%**（帧间运动 1.7–8m），慢速段 **1–8%**。
- 对比模型训练域：20Hz、帧间 0.4–0.8m、真实道路 —— **我们的输入是双重超纲（时间节奏 + 卡通画风）**。

### 3.4 一个推断的因果链
```
机器负载高 → 游戏渲染 7-11fps → 模型收到稀疏+大跳帧的卡通画面
→ 循环状态滑入吸引子（[0.85,0.96,0.90,0.22] + 69m 假车）
→ 覆盖层跳变（闪动或锁定）→ 假车触发莫名刹车/方向
```

## 4. 已实施的两轮修复（及各自的局限）

| # | 位置 | 逻辑 | 局限 |
|---|---|---|---|
| ① | `camera.py` 去重 v3 | 字节级预筛 + 中下部 30–75% 行 Y+UV 场景比较（<0.3% 采样点显著变化 = 重复，不发布） | 拦得住"完全重复"，拦不住"每帧都略有不同"的低信息流 |
| ② | `camera.py` 连贯性门 | 每 ≥1.5s 与 1.5s 前的参考帧比，累计变化 <4% → 不发布（慢爬/冻结燃料） | 行驶中 7–11fps 下每帧 1–8% 变化会通过（它确实是"新"帧） |
| ③ | `modeld.py` 漂移熔断 | (a) 画面中断 >0.5s → 清零循环状态；(b) 输出一字不差 >1.5s → 清零 | 行驶中的漂移是"进出交替"（输出每帧在变）→ 规则 (b) 不触发；帧在流动 → 规则 (a) 不触发 |
| ④ | `modeld.py` 真帧率喂给模型（2026-09-29 深夜，`OP_MODEL_TRUE_TIMING=0` 回退） | 实测输入 7-13fps 而 modeld 硬编码按 20Hz 假设算 `action_t`（帧龄/执行时差）→ 模型运动估计差 2-3 倍 → 状态发散。改为把**真实帧周期**喂给模型（夹在 50-200ms；20fps 时与原值完全一致） | 待实测验证（根因方向） |
| ⑤ | `modeld.py` 漂移指纹即时熔断（`OP_MODEL_DRIFT_RESET=0` 回退） | 指纹 `[0.85,0.96,0.90,0.22]+lead>0.4` 逐字节精确 → 命中**立即**清零状态（不等 1.5s 锁死），把持续 66s 的锁定压成 1-2 帧闪烁 | 治标：打断固定点，不阻止再次进入（与 ④ 配合） |

**新增实测证据（22:18-22:32 用户行驶，修复③已生效仍漂）：**
- 每次**长空档恢复后 3 秒内必漂移**（空档 = 模型无输出 2-644s，恢复即跳）。
- 输入帧率真相：**7-13fps**（帧间隔 78-140ms），帧间变化 1-30%；modeld 的 `frame_delay`/`action_delay` 却按 20Hz 硬编码（50ms/25ms）→ **时差 2-3 倍**（对应修复④）。
- 漂移以"进出交替"出现：如 22:32:29 连续 2 帧指纹 → 1 帧正常 → …（对应修复⑤）。
- 22:31:15-22 还观察到持续 7 秒的**次高状态** `[0.00,0.94,0.95,0.5]`（2 条线 0.95+）——与指纹状态不同，是否也算幻觉待定。

回退开关：`OP_CAM_SKIP_STATIC=0` / `OP_CAM_MIN_MOTION=0` / `OP_MODEL_DRIFT_RESET=0`
熔断已实测生效（日志 `[modeld] 输出锁死 1.6s → 重置模型循环状态`、`画面中断 13.4s → 重置`），**但没能阻止行驶中的漂移**。

## 6. 待解问题（给 GPT 的方向）

1. **离线重放实验**：`probe_frames/` 里有模型真正收到的帧序列。可以用独立脚本把某段序列（漂移前 10 秒 + 漂移段）喂给模型（`driving_supercombo.mlpackage` 或 ONNX），逐帧记录输出，找出**到底哪种输入模式把状态推进吸引子**。这比在线猜测快得多。
2. **输入节奏信息缺失**：模型输入里完全没有"距上一帧多久"。如果给模型喂时间信息（重训）或对低帧率做某种归一化，是否可行？成本？
3. **吸引子逃逸机制**：数据显示"快速大变化帧"能把模型拉出来。能否构造一种**温和的强制逃逸**（不是清零，而是注入几帧"信息量大的真实画面"）？——注意不能凭空造帧（会引入 OOD）。
4. **根因方向（工程侧）**：把游戏渲染率拉回 20fps。可尝试：`takeSnapshot` 用 `snapshotWidth` 降分辨率（模型最终只吃 256×512，几乎无损，但 JPEG 编码省 4 倍 CPU）、降低快照率、游戏画质设置、减少后台进程。
5. **模型层面**：卡通域泛化是天花板。是否值得用卡通渲染数据重训/微调（成本？），或换用对卡通更鲁棒的模型？

## 7. 复现与验证方法

- **注入实验**：往 `~/op项目of all/openpilot/offline_demo/live_frame.jpg` 原子写受控序列（帧素材取自 `probe_frames/` 或 `cv2` 构造），观察 `jump_probe.jsonl` 的输出变化。注意：游戏窗口自己也在写该文件，测试前先确认它的写入节奏（App Nap 时约 1/s，前台时更快），或让测试序列与之兼容。
- **漂移判定**：`laneProbs` 中 ≥3 条 >0.8 且 `leadProb` >0.4（更严格可用精确指纹 `[0.85,0.96,0.90,0.22]` + `leadX≈69.31`）。
- **重启**：`cd ~/op项目of all/openpilot/offline_demo && ./op_app_launcher.sh openpilot (upstream checkout, created by scripts/setup.sh)/offline_demo/live_frame.jpg auto`（绝对路径；约 60 秒全栈起来）。

## 8. 环境约束（重要）

- **M1 / 8GB 内存**，整机已满负荷（swap 2GB+）。不要引入重型依赖（大框架、GPU 重训等）。
- **不能碰用户的鼠标/键盘**：所有注入必须走文件（画面）或页面内合成事件（game_window.swift 里已有 `__opPad.click`）。
- **改生产代码必须**：带注释标签、可用环境变量一键回退、改完必须完整重启栈才生效。
- 用户偏好中文、大白话的沟通；讨厌长时间无汇报。
